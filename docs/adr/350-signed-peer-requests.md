# ADR: a key pair per machine, and signed peer requests instead of a bearer token

**Issue:** #350
**Status:** decided — on the issue's plan; the open choices below were not ruled by the owner and are recorded for review

## Context

A peer authenticates with a long-lived bearer token sent on every request, usually
over plain http on a LAN or VPN. A token captured once works forever, nothing
expires or rotates it, and each direction of each pair is a separate hand-made
secret.

## Decision

1. **Ed25519, standard library only.** One key per machine, generated by the
   service installer, stored owner-only in the state directory, never printed or
   logged. A principal holds a `publicKey` *instead of* a token; the loader refuses
   both and neither. A peer entry says `"auth": "key"` and then carries no token.
2. **Sign in the one place every outbound call passes (`roundTrip`)**, not at each
   call site. Several sites build requests; one that was added later and forgot to
   sign would send an empty bearer.
3. **What is signed:** method, request URI (path and query), sha256 of the body,
   the *receiving* machine's id, the sender's id, a unix time, a random nonce, and
   the relay-assertion headers (on-behalf-of, human-relay, remote-control, acting
   person and issuer). The assertions are covered because on a plain-http hop an
   attacker who cannot forge a signature could otherwise swap one in a request it
   captured. The verifier uses its *own* id as the target, so a request addressed
   elsewhere fails without a target header to trust.
4. **Replay.** ±60 s around the verifier's clock; a nonce is accepted once per
   sender; the cache is bounded and **fails closed** when full — forgetting is the
   replay it exists to stop. A nonce is spent only after the signature verifies, so
   a forger cannot fill the cache. An expiry message names both clocks, because a
   skewed clock otherwise looks like a bad key.
5. **Rotation.** `muster key rotate` makes the new key beside the old one, tells
   every key peer with a request signed by the *old* key, and switches only when
   all have acknowledged. The peer keeps the replaced key for ten minutes and
   stores the rotation in its state directory (overlay on the configured key; the
   configuration wins if an operator re-keys by hand). A retired key may repeat a
   rotation that already happened but may never rotate to a different key, so the
   grace period cannot become a takeover. A machine without a state directory
   refuses a rotation it would forget.
6. **Token peers are untouched**; the bearer path is not reached by a `Muster-Sig`
   header, and a machine may mix both while it migrates. `doctor` and
   `/v1/machines` (`peer.auth`) report the kind.

## What this does not do

- It does not encrypt. Plain http stays readable; capture just stops being useful.
- It does not authenticate responses to the caller.
- An unknown sender and a bad signature read alike, so a stranger cannot
  enumerate machine names.

## Alternatives not taken

- **The peer entry holding the peer's key** (the issue's wording). The receiving
  machine's *principal* entry holds the sender's key — that is what verifies; the
  outbound peer entry only needs to say how to authenticate. Holding the peer's
  public key on the outbound side would verify nothing without response signing.
- **mTLS.** Needs certificates and a CA on a LAN of hand-configured peers, and
  does not fit the plain-http deployment the issue is about.
- **Rotation endpoint reachable by any granted principal.** Rejected: it would let a
  token holder replace a signing key.

## Consequences

- Both machines need clocks within a minute.
- A signed body is read whole (bounded at 8 MiB) before the handler runs, to
  digest it.
